# Каталог ролей: идентичность и границы включения

Задача [#99](https://github.com/glebvin/helios/issues/99), ТЗ v1.0 §5.1/§16, D-01/D-06. Источник бизнес-прав — [матрица ролей](ROLE-ACTIONS-v1.md). Этот документ описывает ограниченный технический шаг, а не готовность всех кабинетов и прав пилота.

## Коды и совместимость

Единый серверный каталог — `apps/api/src/role-catalog.ts`. OpenAPI-схемы Actor и ProjectMembership перечисляют те же20 кодов. SQL013 расширяет только CHECK memberships; пользователей, назначения, сессии и прежние коды не переписывает.

| Состояние | Коды |
| --- | --- |
| Прежние13, поведение обработчиков сохраняется | director, master, worker, pto, gd, ds, zds-sso, zds-soso, supply, safety, hr, admin, customer |
| Новые7, зарезервированы | brigadier, engineer-pto, cost, subcontractor, peo, gb, uo |

`director` означает РП, `gd` — генерального директора. Это разные роли. Синоним `rp` не добавлен: нельзя молча переименовывать существующие записи. `customer` сохранён для прежнего учебного кабинета, но не считается учёткой внешнего СК пилота: там бумажное взаимодействие. ОМТС и кладовщик пока используют один существующий код supply, как в целевой матрице. Флаг pilot обозначает участие роли в целевой спецификации, а не разрешение действия сейчас.

Новые коды могут храниться, входить и читать собственный `/api/v1/me`; также разрешён выход. TenantGuard отклоняет их бизнес-запросы до старых обработчиков, включая legacy `/api`. Неизвестный код отклоняется. Автоматического создания новых учёток нет. UI новых кабинетов этим шагом не вводится.

## Контракты областей

`apps/api/src/role-permissions.ts` задаёт проверяемые контракты для будущих адаптеров операций. Сейчас он не подключён к существующим бизнес-API и не исправляет их прежние ограничения персональных данных. Положительный результат функции сам по себе не активирует новый кабинет.

- Компания обязательна для любого разрешения; чужая компания и неизвестное действие запрещены.
- ГД читает сводки всех объектов своей компании по D-01. Контракт сводок запрещает персональные данные; отдельное право на подробные сведения этим кодом не выдаётся.
- Объектные роли требуют явного назначения на объект. ПЭО/ГБ/ЮО дополнительно требуют явного права просмотра.
- Субподрядчик требует совпадения объекта и работодателя. Бригадный факт дополнительно требует своей бригады; личное задание — своего employeeId.
- Администратор настраивает маршруты в назначенной области; универсального редактирования подтверждённых производственных данных нет.

Адаптер должен загружать активную роль, назначения и принадлежность ресурса из БД внутри аутентифицированной транзакции. Нельзя конструировать AuthorizedScope из body/query или считать присланные projectIds/employerIds доказательством прав. При подключении операции нужны реальные HTTP/SQL-тесты чужой компании, объекта, работодателя и отсутствующего назначения. Состав и поля ответа разрешаются отдельно, а не одним флагом роли.

## Проверка и выпуск

Постоянные тесты: `apps/api/test/role-catalog.test.ts` и `role-catalog-api.test.ts`. Второй тест проверяет настоящие login/me/logout20 ролей, запрещённые действия7 новых ролей, чужую компанию, SQL CHECK и соответствие OpenAPI. CI запускает их в одноразовой PostgreSQL54339; локально разрешён только отдельный каталог `.data/pg-54549`, порт54549. Фикстуры синтетические, тест удаляет только созданные им записи. Повторы/409 здесь неприменимы: новых бизнес-команд нет.

Миграция013 не запускается автоматически при merge. При выпуске сначала установить backend с закрытым доступом новых ролей, затем создавать новые назначения отдельным проверенным шагом. Пока новых назначений нет, старый CHECK и старый backend совместимы с имеющимися данными. Если назначения новых кодов появятся, возвращаться на старый backend опасно: он не знает закрывающего guard. Перед таким откатом нужен совместимый backport guard; удалять назначения ради отката нельзя.
