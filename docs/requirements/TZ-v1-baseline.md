# Правила пилота HELIOS по ТЗ на разработку версии 1.0

Требования пилота существенно определены в исходном документе. Прежние девять вопросов R27 нельзя использовать как общий запрет дальнейшей разработки. Этот документ фиксирует требования, шесть решений владельца от14 ноября2026 и оставшиеся входные данные. Он не выдаёт права в работающем API и не объявляет будущие функции реализованными.

## Основание и приоритет версий

Полностью прочитано «3_ТЗ_HELIOS_на_разработку_v1.0.docx»: версия1.0 от02.11.2026,23 таблицы,188 блоков OOXML, SHA256 `7f315226208feb88218ec03d8c4a62d5926f318a4385b210973d96dd7e1898f5`. Статус в титуле — для запроса коммерческих предложений; §3 называет20 решений окончательными для пилота. Это источник требований, не утверждение о подписании договора.

«2_ТЗ_HELIOS_4.0_с_пометками_изменений (2).docx» того же дня, SHA256 `d397d7a88281aac74b5a4911f25e7cbb7a8bc9324e51bb73236561820d76ff83`, прямо указывает v1.0 как окончательную версию для разработчиков. Поэтому для этого разбора v1.0 приоритетна перед рабочей4.0. «Сводное ТЗ3.0» от31.10.2026 — исторический источник. В найденных исходниках нет tracked insertions/deletions; таблицы читались по строкам/ячейкам, а не по пересказу старого чата. Оригиналы не изменялись и не включаются целиком в Git.

Иерархия: прямое требование v1.0 → заполнение пробела решением владельца → обозначенное техническое решение. Экран или прежнее ограничение сервера не заменяет требование. При обнаружении более новой редакции нужен явный diff и журнал изменений, а не молчаливое объединение несовместимых версий. Цены, гарантийные и коммерческие обязательства этим разбором не пересматриваются.

Прежний roadmap опирался на4.0. Его ссылка «полный пилот19.2» историческая: в v1.0 состав пилота — §4.2/7, функциональные тесты — §19.1, §19.2 посвящён понятности. Номера R/Issues сохраняются; завершённые проверки кода не отменяются и не превращаются в подтверждение новой полноты требований.

## Ответы на прежние девять вопросов R27

1. **Область ГД:** D-01. Для других ролей сохраняется явная область объекта/организации по §5.1; исключение ГД не раздаётся автоматически остальным.
2. **ДС без норм:** контроль объектов и сводка, §5.1. Нормы — этап2; отдельного вопроса о необходимости «норм» для ДС больше нет.
3. **Кто принимает нашим СК:** ПТО. ЗДС ССО контролирует сдачу/замечания; он не подменяет ПТО. Подпись документа требует ещё полномочие по §5.4.
4. **ПТО или ЗДС СОСО для шаблонов:** инженер ПТО готовит, ПТО отвечает, РП/ОТиПБ согласуют, ЗДС СОСО утверждает. Аналогично перечень ИД, но его согласование — РП, внешнее утверждение заказчика — вне системы.
5. **Материалы:** роли и маршрут уже заданы §5.3/11.2. Модель автоматически выводимого результата входного контроля — технический контракт R34 с проверкой всех критичных пунктов и виз; не повод спрашивать заново «снабжение или ПТО».
6. **Охрана труда:** отдельное согласование допуска есть в §5.3. РП остаётся утверждающим; действующий код пока реализует меньше.
7. **Кадры или директор для табеля:** мастер ведёт первичный день; ДП отвечает/утверждает сводный табель; РП даёт данные. Текущая дневная команда director не равна всей целевой модели.
8. **Внешний СК:** без входа в пилоте, результат/скан вносит мастер; guest — этап2.
9. **Администратор:** пользователи/роли/справочники/маршруты, без правки подтверждённого. Дополнительное согласование этого общего принципа не требуется.

Наличие этих ответов снимает прежнюю неопределённость требований, но не закрывает реализацию/тестирование ролей. [Матрица действий и маршрутов](ROLE-ACTIONS-v1.md), [план исполнения и входные данные](EXECUTION-v1.md).

## Что является техническим решением, а не новой волей заказчика

- Раздельные поля «кто готовит», «ответственный Р», «кто фактически выполнил действие»; именно такую информацию содержит таблица5.3. D-02 уточняет отправку первого задания. Остальные конкретные кнопки проверяются по своему маршруту, без превращения Р в лишнего У.
- Снимок версии чек-листа/маршрута для истории документа; новая настройка не переписывает старую приёмку. Для чек-листа это прямой §11.3, для маршрута — способ выполнить аудит/неразрушающие версии §9.
- Связанные принятые части и реестр ИД вместо сложения перекрывающихся площадей актов. Это способ выполнить D-03/T-14, не новая формула стоимости.
- Загрузка скана, сведения о внешних бумажных подписантах и собственная отметка «П» — разные действия. Прямое ограничение §5.4 сохраняется; сам факт загрузки мастером не обходит полномочия компании.
- Пропуск просроченного Д продолжает маршрут с отметкой, но не отменяет критичные требования фронта, материалов, допуска или ИД.
- Новые действия реализуются отдельными server permissions с deny-by-default, UUID/requestId/версией и аудитом. Это согласуется с текущим стилем API, а не разрешает всем read-only ролям любые POST.
