# Проверка модуля «Люди» — R01–R07

Локальный адрес: **http://127.0.0.1:5207**. Серверный стенд пока содержит R01–R03; новые шаги проверяются локально вместе. Это продуктовая оценка базового сценария людей, квалификаций, допуска и назначения. Бригады, весь HR и рабочая смена сюда не входят.

## Подготовка — уже сделана агентом

Создана отдельная синтетическая компания «Локальная проверка раздела Люди», два объекта и три входа: руководитель, прораб и работник. Логины и общий пароль этих трёх тестовых входов находятся в приватном локальном файле «Доступ и начало проверки.md» в папке `.data/people-review` рабочей копии. В GitHub паролей нет. Автоматические проверки используют другую компанию и не заполняют ваш сценарий заранее.

Войдите руководителем. В шапке явно выберите **«Учебная площадка»**. Второй объект специально оставлен для проверки переключения. При смене роли выходите из аккаунта и входите снова. Для одновременной проверки используйте разные профили браузера или другой браузер: вкладки одного профиля делят вход.

## 1. Список и карточка

Откройте «Люди». В компании есть «Иван Работник», «Павел Прораб» и «Мария — карточка без входа». Откройте Ивана, проверьте вкладки, при желании измените телефон. Обновите страницу: сервер должен сохранить правку.

Можно отдельно создать сотрудника с вымышленным именем. Новая карточка сама по себе не создаёт логин. У Марии это уже видно: она нужна для проверки такого различия. Для реального нового входа используется приглашение, а не ввод идентификаторов вручную.

## 2. Доступ к объекту без назначения

Иван → «Документы» → «Доступ и назначение». Учётная запись привязана, доступ закрыт, назначения нет. Откройте доступ кнопкой **«Открыть доступ к объекту»**.

Выйдите и войдите работником. «Учебная площадка» ещё не должна стать доступной: одного доступа учётной записи работнику недостаточно. Вернитесь руководителем и снова выберите объект. Это ожидаемый результат, а не ошибка.

## 3. Настроить правила допуска

«Настройки» → «Шаблон допуска» → «Создать шаблон»:

- Код: `basic`.
- Название: «Базовый допуск».
- Пункт 1: «Инструктаж пройден», критичный.
- Добавьте пункт 2: «СИЗ проверены», некритичный.
- Требуемые коды квалификаций: `safety`.

Сохраните. Должно появиться подтверждение сервера о версии 1. Этот шаблон относится к выбранному объекту.

## 4. Квалификация человека

«Люди» → Иван → «Документы» → «Квалификации» → «Добавить квалификацию»:

- Код: `safety` — точно как в шаблоне.
- Название: «Охрана труда».
- Действует по: будущая дата, например `31.12.2030`.

Сохраните: квалификация должна быть действующей. Реквизит документа — текстовая ссылка/номер, это не загрузка скана.

## 5. Провести проверку

На той же вкладке → «Проверки допуска» → «Новая проверка». Явно ответьте «да» на оба пункта и запишите проверку. В истории должна появиться строка успешной попытки с датой и статусом. Нажмите строку, чтобы раскрыть ответы и подробности. До заполнения всех ответов отправка недоступна.

Квалификация, шаблон и попытка — отдельные записи. Успешная попытка ещё не назначает человека на объект.

## 6. Назначение и вход работника

В блоке «Доступ и назначение» нажмите **«Назначить на объект»**. Дождитесь подтверждения сервера. Ожидается «Назначен на объект» и подтверждение актуальности допуска на момент чтения.

Войдите работником снова: объект теперь доступен. Отдельный интерфейс реальных смен/выдачи заданий будет подключаться последующими задачами; сейчас проверяйте доступ к объекту, а не демонстрационную смену.

## 7. Прораб

Руководителем откройте Павла → «Документы» и откройте ему доступ к объекту. Назначение самого Павла и его проверка допуска для этого сценария не требуются.

Войдите прорабом: объект и назначенный Иван должны читаться. Кнопок назначения, изменения доступа и записи проверки у прораба быть не должно. Вернитесь руководителем для оставшихся действий.

## 8. Отказы и снятие доступа

Выполняйте по одному действию, каждый раз проверяя понятность результата:

1. У Ивана запишите новую проверку с «нет» на критичный пункт. Она должна быть неуспешной; старая успешная попытка не должна разрешать новое назначение. Верните «да/да» **новой попыткой**, затем обновите назначение по последней проверке.
2. Измените срок квалификации на прошедший или отзовите её. Обновите карточку. Назначение может сохраняться, но текущие условия допуска уже не выполнены. Для восстановления исправьте квалификацию, запишите новую успешную проверку и обновите назначение. Сам отзыв квалификации не обещает скрыть объект у работника: это проверка допуска, не команда снятия доступа.
3. **«Снять назначение»**: назначение снято, доступ учётной записи может оставаться открытым. Работнику объект недоступен. Назначьте заново с актуальной проверкой.
4. **«Закрыть доступ к объекту»**: назначение сохраняется, но работник снова не читает объект. Откройте доступ обратно.
5. Перезагрузите страницу или войдите заново. Состояния должны сохраняться. Выберите «Вторую площадку»: у неё собственный шаблон/доступ/назначения, данные первой туда не переносятся.

## Как оценивать и что прислать

Сначала оцените весь связный сценарий, затем отдельно соберём визуальные правки. Для ошибки достаточно: роль → объект → действие → что ожидали → что получилось → снимок экрана. Пароли и токены на снимок не включайте. Отмечайте и непонятные подписи/лишние шаги: это полезный результат продуктовой проверки.

Технические тесты API, прав, повторов команд, конфликтов и мобильной ширины выполняет агент. Вам не нужно читать API или запускать тесты вручную. Проверка владельцем не означает автоматический merge или выкладку. После принятия пакета — отдельное поручение на объединение и публикацию.
