# R30 — непринятый остаток объёма

Основание: main `89736719baadb55194888fc6d9709bd358c0acac`, [#36](https://github.com/glebvin/helios/issues/36), ТЗ v1.0 §6.1/§9 и D-03. Один результат: связанное предъявление непринятого остатка без перезаписи первоначального факта и решения.

## Контракт

Исходный отчёт18 и первое решение17/разница1 неизменны. Действующий мастер объекта предъявляет доработанную часть положительным количеством не больше доступного остатка, с основанием и последним успешным самоконтролем, созданным после последнего решения мастера по этому источнику. Одновременно открыто только одно предъявление остатка.

POST `/projects/{project}/volume-reviews/{report}/remainder`: `requestId`, `expectedVersion`, `action:present|review`, `quantity` — десятичная строка до трёх знаков, `checklistRunId`, `reason`. Present требует основание; review требует причину при неполном/нулевом принятии. Только мастер пишет; остальные читают в прежней области видимости. Версия1 соответствует первому решению, далее2/3 — предъявление/решение,4/5 и т.д. Доступная часть считается как18 минус сумма принятых частей, а не сумма новых предъявлений.

Новый неудачный самоконтроль блокирует действие. Повтор requestId возвращает точную квитанцию после проверки текущих прав; изменённое тело и конфликт версии дают409 без автоповтора. Старые команды, хеши и квитанции не переписываются.

Новая положительная часть получает собственный UUID с FK к источнику и проходит обычный маршрут ПТО. Уже принятые ПТО17 и их история не открываются. В сводке предъявлено18 один раз, принято17 плюс новые части; нулевое решение не создаёт положительную часть. PostgreSQL и существующая десятичная арифметика сохраняют точность.

## Миграции и возврат

029 добавляет неизменный журнал остатка и реестр положительных частей с FK к реальному решению. Первоначальные UUID переносятся без изменения; FK приёмки переключается на реестр. Триггеры проверяют последовательность и предел остатка, FK запрещает положительную часть из нулевого решения. Новые таблицы: FORCE RLS, runtime только SELECT/INSERT.

030 явно запрещает NULL в обязательных полях решения: отдельное дополнение после первого применения029 в собственной QA-базе. Применённая029 и прежние001–028 сохранены. На публичном стенде эти миграции не выполнялись.

В отдельной собственной базе `helios_remainder_pre29` прежний собранный runtime525ef21 создал решения и приёмку на схеме028. После029/030 новая версия сохранила UUID, решения, снимки ПТО и точно повторила реально записанную старую квитанцию. Новая часть довела итог до18.

**Прежний API показывает только первоначальные17 и не является достаточным вариантом возврата для нового остатка.** До выкладки нужен совместимый вариант возврата с корректным чтением новых частей, затем свежий резерв/restore и rehearsal на серверной копии. Production-rollback этим локальным тестом не заявлен.
