# R30 — корректировка принятого количества

Основание: ТЗ v1.0 §6.1, T20, R30/#36. Один результат: мастер исправляет количество конкретной принятой части с основанием, без переписи исходного факта и прежней приёмки.

## Контракт до кода

- `POST /projects/:project/volume-reviews/:report/corrections`: `requestId`, `expectedVersion` (текущая `correction.version` карточки), `previousPartId`, `quantity` (десятичная строка, 0…11 целых и до3 дробных знаков), `checklistRunId`, непустая `reason` до500 символов.
- Только действующий мастер с доступом к объекту. Работник, РП и ПТО читают в прежней области доступа. Нужен последний успешный самоконтроль, созданный после последнего решения мастера, корректировки и события ПТО по этому факту.
- Корректируется только действующая положительная часть данного факта. Отрицательное количество, отсутствие изменения, превышение исходного количества с учётом других действующих частей запрещены. Пока остаток предъявлен и ждёт решения, корректировка недоступна.
- Новая неизменная запись связывает старую часть, новое количество, основание, автора и самоконтроль. Положительное количество создаёт новую часть с новым UUID; ноль снимает старую часть с текущего итога без создания нулевой части. Цепочка может корректироваться далее. Источник, первое решение, остатки и прежние события ПТО не изменяются.
- Сумма и доступный остаток учитывают только действующие части. Любая новая версия количества проходит маршрут ПТО заново. Прежняя приёмка остаётся исторической, не переносится на новое количество. Новые действия по заменённой части получают409 `part_superseded`; точная квитанция ранее выполненного запроса сохраняется после проверки текущих прав.
- `GET` карточки возвращает `currentParts`, `correction` (версия, история, необходимость нового самоконтроля, доступность). Список и итоги отражают действующее количество. Исторические чтения ПТО показывают замену и не предлагают действий.
- Версия корректировки учитывает решения по остатку и корректировки всего факта. Два окна и конкурирующие решения сериализуются общей блокировкой объекта; один запрос записывается, второй получает409. Повтор того же запроса возвращает прежний ответ, изменённое тело с тем же UUID —409. Неопределённый ответ в UI сохраняет исходную команду;409 требует чтения, не автоповтора.

## Совместимость и выпуск

Новая миграция031, применённые001–030 не меняются. Старое API4319832 не учитывает заменённые части и **не является совместимым возвратом после первой корректировки**. До выкладки нужен отдельно проверенный совместимый runtime/план возврата. Этот PR не включает автоматический deploy, очистку данных или новые внешние сервисы.
