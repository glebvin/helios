Один дневной процесс, остальные13 не подключены.

## Пользовательский результат

Администратор выбирает людей дневного маршрута в настройках объекта: мастер, ответственный РП и утверждающий РП. Р и У могут быть одним человеком. После настройки только назначенный мастер отправляет черновик, только назначенный РП утверждает или возвращает с причиной. ПТО и работник не получают права утверждения, другой РП не подменяет назначенного.

В карточке видны текущий держатель, следующее действие, номер попытки и версия настройки. Причина возврата и участники остаются в истории. Новая отправка после возврата создаёт новую попытку с текущей настройкой; старая не переписывается. Изменение настройки не переключает уже отправленный документ на другого РП.

`responsibleUserId` самого задания по прежнему контракту остаётся ответственным за исполнение; это может быть мастер. Он не переименован в утверждающего РП. Фактический отправитель, Р и У хранятся отдельно в маршруте и аудите.

Пока объект не сохранял конфигурацию, прежние задания и их кнопки работают по принятому контракту. После первой настройки старое ожидающее задание без снимка нельзя сразу утвердить: мастер возвращает его в черновик и отправляет заново. Уже опубликованные задания сохраняют статус и старое основание. Редактирование черновиков сохраняет прежние права проекта; отправка по новому маршруту проверяет именно назначенного мастера.

Срок прямо показан как **«Не настроен»**. Календарь/срокиД/напоминания/эскалации остаются в #38 и отдельном срезе; график5/2 не придуман. Это не полное выполнение T-16/R32.

## Атомарность и защита

SQL015 добавляет `daily_task_route_attempts` и `daily_task_route_events`: RLS, FK, SELECT/INSERT приложения без UPDATE/DELETE. Попытка содержит снимок дневной настройки/версии/плана/людей. Событие связано с исходным requestId и receipt, версией задания, переходом и фактическим пользователем. Финальный publication snapshot дополнительно хранит routeAttemptId/routeConfigurationVersion; прежние поля и guards сохраняются.

Переход выполняется внутри существующей TasksService-команды, одной транзакции с receipt, блокировками, readiness, publication snapshot и аудитом. Вложенных вызовов другой публичной команды/отдельного commit нет. Ошибка допуска, фронта, материалов/ИД или пересечения откатывает также попытку/событие/receipt. Неизвестные либо неподключённые обязательные модули по прежнему блокируют публикацию.

Право проверяется заново после ожидания блокировок; core-участники блокируются в существующем порядке проекта/работника/назначений. Повтор успешной маршрутизированной команды сохраняет результат, но заново проверяет активную роль и доступ актёра к объекту. Отзыв доступа РП запрещает и повтор старого receipt. Изменённый payload с тем же requestId —409. Два окна не обновляют expectedVersion автоматически.

При подключении найден конфликт прежнего порядка блокировок конфигурации и задания, если linked user работника — admin. В собственном контуре воспроизведён настоящий deadlock на прежнем `route-config.service.ts`; текущая версия берёт проект до блокировок членства и повторно проверяет доступ после ожидания. Постоянный тест воспроизводит это через реальные SQL gates; это не тест только текста функции.

## Откат: старый backend не должен обходить маршрут

Триггер daily_tasks требует соответствующее событие того же перехода, новой версии и актёра для настроенного объекта/маршрутизированного задания. Утверждение дополнительно сверяет назначенного РП/роль/план. Новый API вставляет событие до UPDATE в той же транзакции. Старый backend этого сделать не умеет и отказывает. Простое увеличение версии при проверке фронта остаётся возможным.

Проверено не только SQL: на отдельной54553 поднят настоящий прежний API из b2f083a (дерево идентично main c0019be). Он читает вход/задание, но publish возвращает422; задание остаётся pending_approval, история содержит одну отправку. Новый API с **тем же requestId** затем возвращает200; появляется ровно одно утверждение. Временный старый процесс остановлен, фикстуры удалены. Это контролируемый отказ старого маршрута, не обещание полного продолжения всех операций при откате.

При UI-проблеме можно вернуть совместимый frontend при сохранённом новом backend. При backend-откате требуется версия с guard новых ролей и сохранённый SQL-барьер; настроенные маршруты могут быть временно недоступны для переходов. Удалять историю/настройку или снимать барьер ради обхода нельзя. До выпуска отдельно фиксируются backup/восстановление, реальные версии и проверенный вариант возврата. SQL013–015 не запускаются на активном сервере от одного merge.

## Воспроизведение и приёмка владельцем

Frozen install, новая БД `HELIOS_DB_PORT=54553 node scripts/db.mjs`, migrate с ADMIN_DATABASE_URL54553, API4387. Запустить API-тест через API tsx loader с TSX_TSCONFIG_PATH=apps/api/tsconfig.json; локально разрешена только `.data/pg-54553`. CI использует одноразовую54339.

Для полного UI: собрать production frontend, поднять preview5254 с proxy на4387; прежнюю сборку —5253 с тем же API. `node qa/daily-route-browser.mjs` сам создаёт и удаляет только собственные фикстуры через `qa/daily-route-fixture.mjs`. До записи проверяются контур/порт/каталог; фикстура сохраняется0600 и не публикуется. Отчёт/снимки — `.data/daily-route-browser/`.

Владельцу после отдельного выпуска: администратором назначить участников **дневного** маршрута; мастером отправить черновик; назначенным РП вернуть с причиной; мастером перечитать и отправить; РП утвердить и открыть историю. Технические проверки запретов/конкуренции уже сделал агент. Реальные аккаунты/данные при этом сохраняются.
