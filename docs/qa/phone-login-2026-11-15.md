# Телефон рабочего: независимая приёмка PR122

Основание — c6b81f4 и первая часть [#106](https://github.com/glebvin/helios/issues/106). Авторский f76cad0 проверен отдельно от отчёта. Это адресное приглашение рабочего, синтетическая проверка кода и дальнейший вход; расширенная матрица/реестр, настоящий SMS, MFA и физический телефон не входят.

## Найденное и исправленное

- 21 авторский API-сценарий проходит. Собственная SQL-фикстура ставила6 неверных OTP-запросов перед правильным под реальным PostgreSQL lock: авторский код всё равно создавал сессию201. Теперь неуспешная попытка коммитится в той же транзакции под удерживаемым row lock; после исчерпания попыток правильный запрос получает401, сессии нет. Результат отказа коммитит только счётчик, до любых записей регистрации.
- 6 разных команд создания давали6 активных приглашений одного телефона. Отдельный барьер таблицы подтверждал гонку нового приглашения с обновлением просроченного. Теперь обе операции используют общий advisory lock по компании/телефону и проверяют действующие записи; остаётся1 приглашение, остальные409.
- Регистрация переписывала кадровое ФИО введённым именем. Привязка теперь сохраняет ФИО и непустой телефон карточки. При принятии карточка заново читается под lock: изменённый после выдачи номер, организация/состояние или уже занятый вход не подменяются. Отказ не оставляет нового аккаунта/идентичности и не расходует приглашение.
- В UI запрос кода после потерянного ответа сохраняет requestId. Новая команда создаётся после подтверждённого ответа либо смены адресата, не при каждом сетевом повторе.
- Четыре прежние проверки OpenAPI уточнены для 81 операции: сохранены точные 58 старых операций, добавлены два auth/phone и один join/challenge. Старые схемы, ссылки и проверки форм не удалены.

Постоянные регрессии: прежний `invitations-api.test.ts` и новый `phone-code-concurrency.test.ts`; всего 24 теста. Барьеры используют настоящие PostgreSQL-соединения, не имитацию успешного ответа. CI запускает их в прежнем server-tests. Локально разрешён только свой54575 с точной проверкой data_directory; CI — одноразовый54339.

## UI и режим провайдера

Production preview проверен Chromium и WebKit на 390 px: создание адресной ссылки, код, принятие, «Моя смена», reload, выход и новый телефонный вход; в обоих запросах challenge моделируется потеря ответа после серверного commit и проверяется тот же requestId. Парольный вход сохранён. Снимки просмотрены; секрет кода в снимок/отчёт не выводится.

`VITE_HELIOS_PHONE_LOGIN=true` явно включает учебный телефонный UI. Только на отдельном QA API задаются `HELIOS_PHONE_PROVIDER=synthetic`, отдельный секрет и закрытый каталог кодов. Никаких реальных SMS или универсального кода. Файл кодов — локальный транспорт одного QA-процесса, не очередь реального провайдера и не доказательство внешней доставки.

Default-сборка сохраняет прежние почтовые приглашения рабочих и вход по паролю: её отдельно проверяет режим `HELIOS_PHONE_QA_MODE=default`. Телефонные кнопки скрыты, незаданный/неподдерживаемый провайдер возвращает503 и не оставляет challenge. Штатное сокрытие5xx (`internal`) не ослаблялось; клиент показывает понятную подсказку. Один frontend-флаг не включает серверного провайдера.

Воспроизведение на собственной папке: установить по lockfile, затем `HELIOS_PHONE_QA_DB_PORT=54575 HELIOS_QA_BROWSER=chromium node --import ./apps/api/node_modules/tsx/dist/loader.mjs qa/phone-login-browser.mjs`. Повторить с `webkit`; default-путь — добавить `HELIOS_PHONE_QA_MODE=default`. Скрипт проверяет точный каталог БД, поднимает production preview и убирает только свои данные/процессы. Не направлять его на общий контур. Физические устройства не проверены.

Приказы PR121 зарезервированы как017, шаблоны Cursor/#35 —018, цены Cursor/#104 —019. Применённые файлы/ledger не переименовываются. Старые экспериментальные QA с016 приказов сохраняются отдельно; итоговый порядок проверяется на свежей копии.

Срез не включает настоящий провайдер, автоматическое повышение роли, восстановление отозванного членства, смену телефона или готовность всего R41/R43. Родители #106/#47 остаются открыты. Финальные SHA/CI/merge и отдельная публикация фиксируются в PR/Release, не выводятся из этого локального отчёта.
