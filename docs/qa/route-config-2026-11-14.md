# R32.1 — версии настройки маршрутов

Задача [#107](https://github.com/glebvin/helios/issues/107), родитель [#38](https://github.com/glebvin/helios/issues/38). Основание: ТЗ v1.0 §5.2–5.3, T-16 и [матрица14 документов](../requirements/ROLE-ACTIONS-v1.md). Это настройка участников; выполнение документов и сроки ещё не подключены.

## Что сделано

В настройках настоящего администратора своего объекта появляется одна карточка. Администратор выбирает документ и конкретных активных пользователей нужной роли/объекта. Составитель отделён от ответственного Р; Р+У могут быть одним человеком. Роли из ТЗ обязательны: нельзя назначить рабочего утверждающим или удалить ОТиПБ из допуска. Дополнительные согласующие допускаются в уже предусмотренных ролях С, всего до3 разных людей; они параллельны. НольС/нольУ сохраняются для документов, где их нет в матрице. Готовность фронта не получает выдуманного утверждения.

К и Д хранятся отдельно от С/У. Внешние бумажные подписи — пояснения источника, а не новые аккаунты и не выданное право подписи. Системная сводка не имеет фиктивного пользователя-составителя.

Конфигурация содержит schemaVersion1 и14 типов. Она может хранить неназначенные места; экран прямо показывает «Не назначен». Это черновая настройка, не готовый к исполнению документ. Подключаемая операция обязана проверить всех необходимых конкретных участников и свои права; отсутствие назначения не разрешает автоматически взять первого директора/ПТО.

Сохранение создаёт отдельную неизменяемую версию. GET с `?version=N` читает старую; новая версия её не переписывает. В UI видны последние50 номеров, старые записи БД сохраняются. История в форме доступна для чтения. На409 автоматического повтора/перезаписи нет. При потере ответа повтор использует прежний requestId; успех показывается только после ответа сервера.

## Серверный контракт и права

- GET/POST `/api/v1/projects/:projectId/route-config`. POST: requestId, expectedVersion, configuration. Схемы и ошибки — `apps/api/openapi.json`.
- SQL014 добавляет только `route_config_versions`: RLS tenant, FK проекта/автора, SELECT/INSERT для приложения, без UPDATE/DELETE.
- Администратор требует активного членства компании и назначения на объект, перечитываемых в транзакции. Назначаемое лицо — активная роль и активный доступ к тому же объекту. Присланный role/scope не выдаёт полномочия.
- Узкое исключение TenantGuard касается только POST route-config для admin. Изменение места, персонала, объёма и табеля администратору этим шагом не разрешается. Новые зарезервированные роли остаются закрытыми от бизнес-API.
- Команда использует существующие durable receipts, блокировку родительского проекта, expectedVersion и аудит в одной транзакции. Повтор возвращает прежний результат, изменённый payload с тем же requestId даёт409.

## Воспроизведение

На новой собственной папке: frozen install; `HELIOS_DB_PORT=54551 node scripts/db.mjs`; migrate с ADMIN_DATABASE_URL только54551. API-тесты запускаются через tsx с TSX_TSCONFIG_PATH=apps/api/tsconfig.json и DATABASE_URL роли helios_app54551. В CI те же тесты принимают только одноразовую54339.

Браузерная фикстура создаётся `routeFixture` из `apps/api/test/route-config-fixture.ts`; её JSON сохраняется локально в `.data/routes-browser-fixture.json` с режимом0600. Поднять API4385 и production preview5252 с proxy на4385; для снимка «до» — прежнюю сборку на5241 с тем же proxy. Выполнить `node qa/route-config-browser.mjs`. Скрипт проверяет свой data_directory/tenant/project до сценария; фиксированные порты нельзя подменять общим стендом. Снимки и results — `.data/routes-browser/`.

Владельцу в готовом preview достаточно: войти учебным администратором, открыть «Настройки», назначить РП дневного задания, сохранить, обновить страницу; выбрать прошлую версию и вернуться к текущей. Логины готовит агент локально, в GitHub они не публикуются. Технические негативные проверки уже выполнены агентом.

## Остаток и выпуск

[#108](https://github.com/glebvin/helios/issues/108) подключает только дневное задание мастер → РП и сохраняет снимок версии. Остальные13 процессов, таймеры/календарь/Д/уведомления остаются в #38 и профильных задачах. Утверждение допуска, сводный табель ДП, действующие приказы и бумажная подпись этим PR не реализованы. Пустой календарь не заменяется5/2.

Merge отдельно от deploy: на активном сервере SQL014 и новые учётки этим документом не запускаются. Таблица добавочная; пока исполнения маршрутов нет, прежние обработчики не читают её, откат на совместимый backend с guard новых ролей сохраняет версии неиспользованными. После #108 совместимость отката проверяется заново: старый API не должен обходить согласование. Перед backend-выпуском нужны резерв, фактическая совместимая версия возврата и smoke без reset/seed.
