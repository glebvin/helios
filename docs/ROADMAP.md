# Roadmap HELIOS: подключение прежнего интерфейса

**R01–R03 технически проверены. Текущее объединение — в PR #28–#30, выкладка — в GitHub Releases. R04 реализован и технически проверен в рабочей ветке, ожидает review; [отчёт и снимки](qa/r04-qualifications-2026-11-11.md). R04 ещё не опубликован.** В этом roadmap нет задания «переписать весь frontend». Карточки — будущая работа; организация репозитория не означает их реализацию.

Основные роли: **руководитель проекта (rp/director), прораб (master), работник (worker), ПТО (pto)**. Они покрывают подготовку, исполнение и контроль рабочего дня. ПТО пока не получает несуществующий серверный процесс принятия качества.

## Как использовать без ручного аудита

Откройте следующее действие в NEXT.md и соответствующую карточку → скопируйте блок для Cursor → получите от агента проверенный preview/PR → оцените внешний вид и удобство → примите шаг. Агент сам исследует API, готовит отдельные QA-данные и выполняет технические/браузерные проверки.

Полный запуск всех карточек сразу запрещён правилами проекта. Сроки в часах не выдумываются: размер уточняется после просмотра разрыва конкретного шага. Если шаг оказался большим, сначала разделить его, сохранив критерии и зависимости.

## Контрольные результаты

1. **R01–R08:** правильный пользователь/объект; человек подготовлен к заданию. Параллельные зависимости в таблице не требуют параллельной разработки: по умолчанию WIP=1.
2. **R09–R12:** руководитель публикует задание в прежнем интерфейсе; назначенный работник его видит.
3. **R13–R17:** работник проходит реальную смену и отправляет объём/файл; руководитель видит факты.
4. **R18–R22:** часы проверены, Excel согласован, сводки не противоречат данным, ПТО видит доступные факты.
5. **R23–R26:** доставка, запуск/обновление и сквозной сценарий проверены в браузерах; физические устройства подтверждены отдельно.
6. **R27:** утверждены права остальных девяти ролей и границы следующих серверных модулей.

## Что остаётся дальше

Серверные процессы качества/замечаний, материалов/входного контроля и исполнительной документации/актов требуют отдельных контрактов и задач. Кабинет с названием роли не доказывает готовность её действий. Бригады, сложные назначения, развитие приглашений и администрирования — дополнительные ограниченные задачи после основного прохода, по подтверждённой необходимости.

Не расширять backend и права скрытно в UI-карточке. Не снимать блокирующие требования материалов/ИД, чтобы демонстрация прошла.

## Как обновлять статус

R01–R03 помечены verified: технические и браузерные проверки выполнены, отчёты находятся в карточках. Не писать их повторно. verified фиксирует проверку; факт merge определяется соответствующим PR, факт deploy — выпуском и живой версией стенда. R04 находится в review, его реализацию не повторять. Остальные ждут зависимостей или отдельного поручения. После приёмки шага агент обновляет его карточку и соответствующий issue, затем помечает следующий доступный шаг ready. Автоматическое управление зависимостями здесь не настроено. Зависимость считается закрытой по реальной приёмке, а не по наличию коммита.

Готовность определяется [Definition of Done](DEFINITION-OF-DONE.md), а карта фактических разрывов — в [ROLE-FLOW-MAP](ROLE-FLOW-MAP.md). [Правила GitHub для владельца](GITHUB-FOR-OWNER.md).
