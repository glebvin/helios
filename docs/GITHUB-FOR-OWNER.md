## Слова без расшифровки аббревиатур

| Слово | Значение |
| --- | --- |
| Git | История изменений на компьютере |
| GitHub | Хранение и совместный просмотр проекта в интернете |
| Repository | Проект и его история |
| Branch / бранч / ветка | Одно и то же: линия изменений всего проекта |
| Commit | Сохранённое изменение с описанием и точным ID |
| Push | Отправить коммиты в GitHub, не выложить сайт |
| Fetch | Получить сведения об удалённых версиях, не сбросить свои файлы |
| Pull | Получить и интегрировать изменения локально; при несохранённой работе агент сначала проверяет состояние |
| PR | Предложение объединить изменения; место проверки |
| Merge | Объединение; у нас squash сводит задачу к одному итоговому коммиту |
| CI / Checks | Автоматическая проверка кода |
| Deploy | Запуск выбранной версии на сервере |
| Tag / release | Именованная отметка точной версии и описание |
| Revert | Новое изменение, отменяющее выбранную правку; обычно предпочтительнее переписывания общей истории |

## Один цикл вашей работы

1. Откройте roadmap и первую незавершённую готовую карточку. В один момент активна одна задача.
2. Скопируйте блок «Готовое задание Cursor». Агент сам проверит папку, зависимости, создаст ветку и выполнит техническую работу.
3. Агент должен вернуть ссылку на PR, работающий preview, снимки до/после и фактические проверки. Ответ «готово, build зелёный» недостаточен.
4. Откройте preview и оцените понятность и внешний вид нужного сценария. Если не устраивает, напишите конкретную правку в том же чате/PR, не создавайте новую параллельную реализацию.
5. В PR проверьте base: main, название/объём, Checks и Files changed. Непонятное масштабное изменение вернуть на объяснение/разделение.
6. После готовности разрешите объединение PR. Кнопка Squash and merge объединяет код, не очищает базу и не означает deploy.
7. Отдельно поручите выложить принятый commit на тестовый стенд. Агент фиксирует предыдущую версию и проверяет публичный результат.
8. Следующая задача начинается от обновлённой main.

Владелец принимает продуктовые решения; агент выполняет техническую проверку. Требовать одобрения второго человека, которого нет, бессмысленно. Самопроверка агента не называется независимым ревью.

## Если случилась ошибка

- До merge — поправить рабочую ветку; основная версия не затронута.
- После merge, до выкладки — исправляющий PR или revert конкретного PR.
- После выкладки — вернуть проверенную предыдущую версию с учётом совместимости БД; не запускать reset.
- При конфликте веток — агент сначала объясняет, какие изменения столкнулись. Владелец не выбирает «Accept all» наугад.
- При красном CI — открыть причину, исправить именно её и повторить. Не отключать проверку для зелёного значка.
- При старом экране — проверить commit в preview/сервере и рабочую ветку. Название вкладки GitHub не доказывает версию сайта.

## Правила, которые экономят нервы

Одна задача/ветка/PR; русские понятные названия результатов; код без паролей; отсутствие force-push и очисток базы; отдельные UI и функциональная приёмки; опубликованная версия записана; исторические ветки обозначены archive. Количество документов и badges не доказывает качество — доказательство в воспроизводимых проверках.
