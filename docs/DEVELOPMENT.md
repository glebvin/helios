# Разработка и проверки

## Требования

Node.js 24, Corepack 0.35.0, pnpm из packageManager (12.18.0). Зависимости ставятся по pnpm-lock.yaml. PostgreSQL должен быть отдельным для разработки/QA. Адреса и пароли активного стенда здесь не публикуются.

```sh
corepack pnpm install --frozen-lockfile
python3 scripts/check-docs.py
node scripts/check-types.mjs
corepack pnpm --config.verifyDepsBeforeRun=false --filter @helios/web build
corepack pnpm --config.verifyDepsBeforeRun=false --filter @helios/domain test
```

Пакет domain пока использует явный typeRoots к установленным типам API; это известное ограничение структуры зависимостей, отражённое в scripts/check-types.mjs. Не исправлять соседние зависимости вместе с UI-задачей без причины.

## Локальные сервисы

`scripts/db.mjs` запускает embedded PostgreSQL в .data, по умолчанию порт 54329; HELIOS_DB_PORT позволяет отдельный контур. Скрипт проверяет каталог занятого порта. Не запускать его как способ заменить существующую базу.

API использует ADMIN_DATABASE_URL для миграций и DATABASE_URL для ограниченного приложения. Переменные задать только для своего отдельного контура. Перед migrate/seed проверить host, port, database и отсутствие активных пользовательских данных. Дефолтный seed создаёт учебные учётки, а не текущие 13 кабинетов.

`corepack pnpm dev:api` — API; `corepack pnpm dev:web` — Vite; `corepack pnpm dev:worker` — фоновые задания. API_PORT задаёт API, HELIOS_API_ORIGIN задаёт proxy Vite, HELIOS_WEB_PORT — порт интерфейса. По умолчанию Vite ожидает API на 4341, интерфейс 5184. Адреса согласовать между процессами, не менять общий конфиг ради одного локального запуска.

## Серверные тесты

`corepack pnpm --config.verifyDepsBeforeRun=false --filter @helios/api test` пишет синтетические данные и проверяет миграции. Нужны применённые миграции, базовая учебная фикстура, ограниченная роль helios_app с RLS. Несколько исторических тестов повторной миграции жёстко используют 127.0.0.1:54339/helios, поэтому не запускать полный набор против произвольного или занятого контура.

GitHub Actions создаёт одноразовый PostgreSQL 17 на этом порту и отдельную роль, затем migrate, seed и последовательные тесты. Пароли в workflow относятся только к одноразовой службе runner и не дают доступа к стенду. Нет server/SSH secrets и автоматической выкладки.

## Что покрывает CI

- Ссылки входных документов, связи с ТЗ и зависимости 51 карточки.
- TypeScript API/web/domain/offline.
- Production Vite build и domain-тесты.
- Frontend-тесты `apps/web/src/*.test.ts` через встроенный Node test runner.
- Серверные API-тесты в изолированной БД.

CI не покрывает внешний вид, весь сквозной UI, физические телефоны и полноценный офлайн. Локальные и браузерные проверки шага остаются обязательными.

## Offline-модуль

Browser-тесты требуют Playwright ровно 1.62.1, HELIOS_PLAYWRIGHT_MODULE и PLAYWRIGHT_BROWSERS_PATH; подробности в [offline-queue](offline-queue.md). Полный набор модуля включён в offline-checks; пропуск не считается успехом. Очереди и ограниченная оболочка R23–R25 прошли [отдельную приёмку](qa/offline-release-r23-r25.md); физические устройства — отдельная проверка R26.


В локальных копиях с уже установленными/связанными node_modules используйте --config.verifyDepsBeforeRun=false: иначе pnpm может попытаться автоматически переустановить зависимости до запуска команды. Это не замена install --frozen-lockfile в чистом CI.

Для CI/Linux разрешён postinstall уже закреплённого @embedded-postgres/linux-x64, аналогично существующему darwin-arm64. Неизвестные build-скрипты по-прежнему запрещены; global ignore-scripts/dangerouslyAllowAllBuilds не включались.

CI использует внутренний и внешний порт 54339 и PGDATA с окончанием codex-api/.data/pg-54339, сохраняя существующие предохранители тестов. Не подменять их универсальным разрешением любой БД.

## Браузерный и offline CI

В workflow `Проверки HELIOS` четыре прежних job запускаются независимо: `project-checks`, `server-tests`, `browser-smoke`, `offline-checks`. У каждого job своя VM, а у интеграционных — свой PostgreSQL; одинаковые loopback-порты между VM не конфликтуют. Их состав, команды, версии и предохранители БД сохранены. Дополнительные job [резерва](../deploy/backup/README.md) и [учебного S3](../deploy/evidence/README.md) их не заменяют: полный результат требует успеха этих четырёх и job `backup-restore`, `s3-evidence`.

Два браузерных job:

1. `browser-smoke` собирает production frontend, запускает Vite preview и настоящий NestJS на одноразовом PostgreSQL. `qa/ci-smoke.mjs` проверяет вход, объект, список, создание сотрудника через UI, чтение новым входом/после reload, запрет прямой записи другим ролям, 390 px, сетевую ошибку/повтор и истечение сессии.
2. `offline-checks` на другой одноразовой БД запускает `packages/offline/test/browser.test.mjs all`: весь набор сценариев в Chromium/WebKit, включая очередь событий/Blob, повторы, потерю ответа после commit, версии и контекст пользователя; часть проходит через настоящий NestJS/PostgreSQL.

Playwright закреплён в devDependencies и lockfile на 1.62.1, браузеры устанавливаются той же версией. Checkout CI размещён в `codex-api`, а `PGDATA` сервиса совпадает с абсолютным путём fixture: существующие проверки идентичности тестовой БД не ослаблены. Сценарии одной БД выполняются последовательно. Ни job, ни тесты не получают SSH, учётки или адрес стенда для записи.

GitHub сохраняет синтетические результаты, снимок и диагностические логи smoke, TAP offline на 7 дней. Не добавлять в эти артефакты session/token dump, рабочие данные или `.env`. Ошибка теста завершает job с ненулевым кодом; upload выполняется и при ошибке.

Для локального запуска используйте отдельную одноразовую БД, **не текущую рабочую 54339**. `prepare-ci-db.mjs` разрешён только GitHub Actions и намеренно откажет локально. Smoke требует явного `HELIOS_CI_FIXTURE=disposable` и фиксированного loopback API. Offline требует существующих защит fixture; не заменяйте их произвольным DATABASE_URL. Полный воспроизводимый прогон доступен в Checks PR.

Эти проверки не доказывают холодный запуск всей PWA или готовность будущих экранов. Приёмка очередей/ограниченной оболочки R23–R25 отражена в отдельном отчёте; физические Android/iPhone — R26, человеческий UX — R39, весь пилот — R50. Ни merge, ни CI не публикуют сайт автоматически.

## Быстрый рабочий цикл без сокращения приёмки

- Во время реализации запускать проверку изменённого поведения и связанные быстрые проверки. После успеха сохранять результат, а не повторять тот же прогон без нового кода, сбоя или изменения окружения. Перед merge обязательны четыре прежних CI job и job резерва текущего кандидата.
- `node scripts/check-types.mjs` проверяет все четыре прежних проекта, по два компилятора одновременно. `--noEmit` исключает общую папку результатов. При нехватке памяти использовать `HELIOS_TYPECHECK_CONCURRENCY=1 node scripts/check-types.mjs`. Ошибка любого проекта даёт ненулевой exit code; остальные результаты не скрываются.
- Сначала подготовить сценарий/роль/отказ из контракта и данные скриптом из репозитория, затем собрать preview и проверить его версию. Не пересобирать папку, из которой идёт браузерный прогон. Базовый и новый preview держать отдельно; не переключать исходники/сервер под активным тестом.
- Сценарии с общей БД или управляющим fault proxy идут последовательно. Параллельны только доказанно независимые контуры; отсутствие `needs` в CI не разрешает гонку локальных скриптов на одном порту.
- Новый дефект сначала воспроизвести узким сценарием. После исправления повторить его и затронутые соседние проверки. Перед сдачей выполнить подходящий общий прогон финальной сборки и CI. Исследовательские скрипты, нужные повторно, сохранять в репозитории.
- После чисто документального коммита локальный E2E может оставаться доказательством предыдущей реализации: указать фактически проверенный SHA, текущий HEAD и проверенный diff между ними. Не переименовывать старый прогон в новый. Изменение приложения, общих компонентов, API/domain, конфигурации, lockfile, фикстур или сценария требует пересмотра затронутой проверки. При сомнении повторить. CI текущего HEAD не заменяется старым.
- В передаче PR оставить краткий результат, версию и применимые проверки по [шаблону](PR-HANDOFF.md). Большой отдельный отчёт нужен для сложной приёмки, а не для каждой кнопки. Успешные локальные проверки до push уменьшают число дорогих неудачных CI-прогонов.

Оптимизация сохраняет полный состав CI; она сокращает ожидание независимых jobs и повторную ручную подготовку. На плохом PR независимые jobs могут потратить больше runner-минут, чем прежняя цепочка с ранним пропуском. Таймауты, отмена устаревшего запуска при новом push и изоляция данных остаются включёнными. Сокращение тестов, отключение WebKit, слепые retries или `continue-on-error` ускорением не считаются.
