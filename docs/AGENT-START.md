# Как агенту взять задачу HELIOS

Одна работа — один наблюдаемый результат. Живой статус и обязательный остаток ведутся в существующей GitHub Issue; [roadmap](ROADMAP.md) объясняет требования, [NEXT](../NEXT.md) указывает ближайшее действие. Этот документ не поручает выполнить весь roadmap, merge или deploy.

## До кода

1. Прочитать AGENTS, CONTRIBUTING, NEXT, выбранную Issue **с последними комментариями**, карточку и раздел [ТЗ v1.0](requirements/TZ-v1-baseline.md). Зафиксировать применимые T/D, основной сценарий и границу. Историческая4.0 не меняет действующую1.0.
2. Проверить `git status`, remote, ветку, HEAD; выполнить `git fetch origin`, сравнить с origin/main. Найти открытые PR по Issue и модулям. Чужую папку/preview не переключать и не сбрасывать. Новая работа — отдельный worktree и понятная `codex/<задача>`.
3. В Issue записать срез: **роль → действие → серверный результат**, зависимости с PR/SHA, что уже есть, что не входит,3–6 проверяемых критериев. Если результат написан — проверять/доработать его, а не создавать дубль.
4. Сверить OpenAPI, controller/service, SQL и связанные чтения. Установить переходы, права, версии, requestId, ошибки и историю. Scope из клиента не доказывает полномочия. Номер новой миграции сверить с открытыми PR и ledger; применённые файлы не переписывать. Указать совместимость возврата.
5. Самому подготовить синтетические данные, свободные порты и отдельную БД по [DEVELOPMENT](DEVELOPMENT.md).13 входов стенда не покрывают все роли: СО/инженеру ПТО нужен свой QA-пользователь, а не переименование director. Для П требуется действующий приказ.

Срез готов к реализации, когда понятны источник правильности, контракт и проверка. Разделить **предпосылки кода**, **условия merge**, **входы реального пилота**. Открытая крупная R32 не запрещает использовать уже принятую конфигурацию маршрутов. Но интеграционный запрет нельзя объявить проверенным без обоих реальных путей.

Без образца заказчика/доступа к SMS/storage можно проверить синтетический контракт; нельзя выдавать его за совместимость с реальным форматом/провайдером. Не спрашивать повторно шесть решённых бизнес-вопросов. Новое неизвестное правило не угадывать: сформулировать конкретный вопрос и продолжать независимую работу.

## Реализация и проверка

- Сохранить принятый UI и существующие тесты. Не расширять роли и не отключать guards ради демонстрации.
- Проверить основной, отрицательный и затронутый соседний путь. Запись подтвердить повторным чтением/reload; права — прямым HTTP-запретом; команды — точным повтором после потерянного ответа и конфликтом версий по риску. Отказ не оставляет частичных бизнес-записей. Итоги сверить с независимым числовым примером ТЗ.
- UI открыть в браузере на подготовленных данных: сохранение, ошибки,390px, длинные значения, клавиатура. Физический телефон,24ч offline и проверка людьми — отдельные доказательства. Успех после сервера, локальное ожидание подписано.
- Следовать быстрому циклу DEVELOPMENT: точечная проверка →общий кандидат. Все **шесть обязательных CI текущего SHA** сохраняются. Изменение основания требует оценки затронутого поведения. Скрипт в `qa/` не означает запуск в workflow. Для документов достаточно проверки ссылок/согласованности, runtime-тесты не выдумывать.
- Существенную исправленную ошибку закрепить воспроизводимой регрессией. Тест должен отличать правильное поведение от ошибки. Данные готовит агент, владелец оценивает понятность и вид.

Передать PR по [PR-HANDOFF](PR-HANDOFF.md): точный SHA/base, условия→действие→ожидаемое→фактическое, команды подготовки данных/проверок, CI отдельно от локального, preview, риски и остаток. Владельцу дать3–5 действий на готовых данных. В публичный репозиторий не помещать секреты/реальные ПД; локальная `.data` не единственный источник повторяемого теста.

## Завершение

Написано, проверено, принято, объединено, опубликовано — разные факты. Issue закрывается по всем её критериям; частичный PR содержит обычную ссылку без автоматически закрывающего ключевого слова. Подпункты отмечать внутри существующей Issue. Зависимая цепочка PR не заменяет принятый пользовательский путь.

После передачи остановиться в пределах поручения. Проверяющий сверяет текущие SHA и совместимость с main. Блокер одного независимого PR не блокирует остальные. После squash родителя обновить base/diff дочернего и сохранить собственные изменения и все родительские тесты. Переданную ветку не переписывать без координации.

Выпуск выбранного принятого commit — отдельно: резерв/restore, миграции и совместимый возврат, frontend/API/worker, публичный smoke. Старый образ после новых записей может не подходить; использовать проверенный вариант Release. Возврат приложения не равен восстановлению старой БД. Никакого seed/reset стенда.

## Промпт для Cursor

> Возьми Issue #<номер>, только результат «<один сценарий>». Прочитай AGENTS.md, NEXT.md, docs/AGENT-START.md, актуальную Issue с комментариями и карточку. Проверь свежую main и открытые PR: существующий результат не дублируй. В отдельной папке и понятной ветке codex/<название> зафиксируй срез, зависимости и критерии, затем реализуй оставшееся. Сохрани UI, права, тесты и историю. Сам подготовь изолированные QA-данные, проверь основной, отрицательный и соседний пути. Передай PR по шаблону с SHA/base, воспроизводимыми проверками и остатком. Следующую крупную функцию, merge и deploy автоматически не начинай.

Основания процесса: [ясная задача и критерии для агента](https://docs.github.com/en/enterprise-cloud%40latest/copilot/tutorials/cloud-agent/get-the-best-results), [небольшие PR](https://docs.github.com/en/pull-requests/concepts/helping-others-review-your-changes), [явные зависимости Issues](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-issue-dependencies). Текст инструкции сам по себе не устанавливает автоматические gates или диспетчер агентов.
