# Передача задачи от реализации к проверке и выпуску

Основная передача — описание PR по [шаблону](../.github/pull_request_template.md). Оно содержит текущее состояние результата. Подробные повторяемые сценарии дополняют существующие [тест-кейсы](test-cases/README.md); инструкции и фикстуры для автоматических тестов сохраняются в репозитории. Отдельный отчёт нужен для сложного пакета или существенного исследования, а не для каждого коммита.

У завершённых PR передача дополняется датированной ретроспективой по отчётам, точным Checks и Releases; исходное описание сохраняется как историческое. Проверка источников не является новым E2E-прогоном. Отсутствующий/красный CI исходного head нельзя заменить зелёным статусом позднейшего пакета без указания его версии. [Сверка завершённых R01–R22](qa/retrospective-handoff-2026-11-13.md).

## Что передаёт исполнитель

1. **Результат и границу.** Роль, пользовательское действие, что изменилось, issue и зависимые PR. Для шага roadmap — раздел ТЗ v1.0, T-сценарий/решение D по применимости, реализованная часть и обязательный остаток по [карте пилота](roadmap/PILOT-19.2.md).
2. **Проверенную версию.** Полный SHA, base PR, preview и версия сборки. SHA и ссылки CI обновляются в теле PR после последнего коммита. Работающий preview другой версии не подтверждает новый код.
3. **Факты проверки.** Условия/роль → действие → ожидаемый результат → фактический результат, команда или ссылка на доказательство. Пустые данные не подтверждают непустой сценарий, скрытая кнопка не подтверждает серверный запрет, эмуляция не подтверждает физический телефон.
4. **Оставшуюся работу проверяющего.** Конкретные риски, пробелы и проверки при совмещении. Для непроверенного — причина и влияние. Не ограничиваться фразой «проверь всё».
5. **Короткую проверку владельца.** 3–5 действий и ожидаемый результат на подготовленных агентом данных. Владельцу не нужно изучать API, создавать фикстуры или восстанавливать окружение.

Для функциональной правки выбираются значимые основной, ошибочный и соседний сценарии. При изменении контекста/прав/записи учитывать поздние ответы, другой объект или вход, обновление, повтор и конфликт — по риску изменения. Для текста/отступа достаточно подходящей проверки ссылки/вида; неприменимость поясняется кратко. Заполнять одинаковую матрицу всех ролей для каждой мелочи не требуется.

## Что остаётся в автоматической регрессии

Каждая существенная найденная ошибка должна получить воспроизводимую проверку поведения либо явную причину, почему это пока невозможно. Предпочтителен самый простой уровень, который ловит ошибку: unit/API/браузер. Не писать тест, который повторяет детали реализации и не отличает исправное поведение от ошибки.

В PR различать:

- **Автоматически в CI:** точный тест и запускающий его workflow / команда.
- **Воспроизводимо локально:** команды, зависимости, подготовка отдельной БД/данных, адреса через параметры или переменные окружения.
- **Проверено разово:** что делалось, результаты, что мешает повторению и существующая задача для важного пробела.

Повторять уже успешный неизменный локальный сценарий без причины не требуется. Если после него поменялись только документы, сохранить исходный SHA прогона и показать проверенный diff до нового HEAD. Изменение приложения, общих зависимостей/контракта, окружения, фикстуры или теста требует пересмотра затронутых доказательств; при сомнении повторить. Все обязательные job текущего workflow должны пройти на кандидате: четыре базовые, backup-restore и s3-evidence.

Наличие скрипта в `qa/` не означает его запуск в CI. Одна ссылка на файл в `.data/` или `/private/tmp` не обеспечивает повторение на другой машине. Повторно используемые сценарии и подготовку синтетических данных переносить в репозиторий без паролей, токенов и клиентских данных. Не исправлять этот пробел seed/reset общего стенда.

Например, для «ПТО скачивает файл» нужны готовый файл на отдельном QA, подтверждённые байты скачивания, неприменимость действия к незавершённой загрузке и применимый запрет чужого объекта. Если проверено только пустое состояние — так и написать.

## Как работает проверяющий

- Сверяет требования, diff, HEAD и реальную base; отчёт автора служит указателем, а не заменяет собственную проверку.
- Проверяет заявленные доказательства и существенные оставшиеся риски, выбирает собственные сценарии. Успешные проверки неизменного кода без новой причины не повторяет; самопроверку автора не называет независимым ревью.
- При новом коммите или изменении основания оценивает затронутые сценарии и итоговое дерево. Прошедший CI старого HEAD не подтверждает новое объединение.
- В конце обновляет передачу: что подтверждено на каком SHA, что исправлено, что осталось и блокирует ли это выпуск. Незакрытый обязательный критерий не превращается в «готово» от переноса в другую issue.

## Связанный пакет и следующая задача

Для согласованного пакета можно провести одну общую приёмку. Зафиксировать SHA всех входящих PR и свежей main, собрать отдельную ветку с учётом зависимостей, сверить каждый diff и проверить спорные сценарии. Все шесть CI запускаются на итоговом кандидате. Общие сборку, smoke и регрессию отдельных веток повторять не требуется. Правки, затрагивающие поведение или итоговое дерево, проверяются на новом кандидате.

Перед объединением сверить текущие SHA и дерево, на котором прошёл CI. Когда правила ветки позволяют, обновление main с сохранением исходных коммитов оставляет дочерние PR видимыми как объединённые. Если требуются отдельные проверки репозитория, соблюдать их. Блокирующую ветку оставить вне кандидата вместе с её зависимыми ветками. Выкладка проверяется отдельно.

Сохраняется ограниченный пакет, разрешённый владельцем. Каждый шаг имеет свой сохранённый результат и техническую проверку; продуктовая оценка связанных шагов возможна вместе. Исполнитель не меняет переданные ветки, пока проверяющий выпускает предыдущий пакет. Следующие разрешённые шаги берутся из текущего [NEXT](../NEXT.md), поручения и зависимостей, а не выводятся автоматически из номера задачи.

Новый важный баг фиксируется в существующей подходящей issue или отдельной задаче по правилам проекта; ссылка остаётся в PR. Наличие задачи не означает, что проблема устранена. Не создавать второй roadmap или очередь в чатах.

## Передача после выпуска

Ответственный за выпуск указывает финальный commit, опубликованный адрес и Release, совместимость данных, предыдущую версию и способ отката, результат smoke на опубликованной версии. Base/head PR, main и сервер могут различаться. [Merge и deploy](BRANCHES-AND-RELEASES.md) выполняются в пределах поручения; описание PR не разрешает выкладку автоматически.

Шаблон помогает не терять контекст. Он не является программным запретом merge и не гарантирует качество заполнения. Для будущего автоматического gate нужно отдельное изменение CI с проверкой фактических данных, а не только наличия заголовков.
