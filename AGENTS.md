# Правила работы с HELIOS

Актуальные инструкции владельца имеют приоритет. Эти правила сохраняют принятый интерфейс и ограничивают объём задач.

1. Прочитать README.md, CONTRIBUTING.md, docs/ROADMAP.md и карточку текущего шага. Один шаг за один проход; не выполнять весь roadmap по одной просьбе реализовать карточку.
2. Проверить папку, текущую ветку, git status и свежую main. Не сбрасывать чужие/несохранённые изменения. Работа в отдельной ветке codex/<понятная-задача>, при необходимости — в отдельном checkout.
3. Архивные ветки — исторические источники. Не объединять их целиком с main и не заменять из них экраны ради подключения API.
4. Сохранить утверждённые компоновку, палитру, компоненты и навигацию. Перед UI-правкой снять до; после — проверить те же данные, роль, тему и размер окна. Новые обязательные поля/ошибки оформлять в существующем стиле.
5. Перед кодом установить точный контракт: поля, действия, роли, версии, причины отказов и связанные чтения. Использовать существующий клиент. Не отключать серверные проверки и не выдавать всем director/pto.
6. Серверные бизнес-данные не подменять localStorage. Успех показывать после подтверждения; queued/offline обозначать отдельно. Повтор команды сохраняет её идентичность; конфликт версии не исправлять слепым повтором.
7. Писать соразмерные проверки поведения. Сборка не доказывает готовность UI. Агент выполняет браузерный сценарий, обновление, другой уполномоченный вход, запрет роли, повтор/ошибку и проверку телефонной ширины; отсутствие проверки сообщает явно.
8. Не запускать seed, reset, down -v или миграции на активном стенде в задаче по UI. Тесты выполняются только в отдельном контуре. Секреты, токены и реальные клиентские данные не коммитить.
9. Один PR — один ограниченный результат. Название по-русски, ссылка на issue/карточку, проверки, preview/снимки и ограничения. Не менять нерелевантные зависимости/форматирование/архитектуру.
10. Merge и deploy — отдельные действия. Без поручения не публиковать приложение. При разрешённой выкладке зафиксировать коммит, совместимость миграций, резерв и проверяемый способ отката, затем проверить публичный результат.
11. При завершении обновить статус именно выполненного шага и документы текущего состояния. Исторические отчёты не переписывать задним числом.
