На сервере по-прежнему R01–R03: frontend/main21b4bde, API/worker1658687. [Releases](https://github.com/glebvin/helios/releases) и живой `/release.json` определяют размещённую версию.

**Пакет R04–R06 подготовлен для общей оценки владельцем.** [R04/PR32](https://github.com/glebvin/helios/pull/32) — квалификации; [R05/PR33](https://github.com/glebvin/helios/pull/33) — шаблон; R06 — попытки проверки допуска, ветка `codex/proverka-dopuska`, [карточка](docs/roadmap/steps/R06-proverka-dopuska.md), [общий отчёт/снимки](docs/qa/r06-admission-2026-11-12.md). Повторно реализации не писать. Владелец разрешил сделать третий шаг до оценки всего пакета; это не означает принятие или разрешение deploy.

Ветки связаны32→33→R06: PR33 base `codex/kvalifikatsii`, R06 base `codex/shablon-dopuska`. Общий preview включает все три шага, каждый PR показывает собственное изменение. Обновлённое основание R05 —97f6000 с успешным CI, а не прежний298b9dd. PR58 про покрытие пилота/CI отдельно и в пакет не включён.

Теперь владелец может пройти общий сценарий: «Настройки → шаблон», затем «Люди → сотрудник → Документы → квалификация/проверка». Агент уже проверил API, ошибки, повтор без дублей, роли, конфликт шаблона и390px. Passed snapshot — история, не утверждение текущего доступа на объект.

Следующее действие — ревью/оценка пакета. Merge и deploy выполнять только по поручению. Перед squash родителя перевести дочерний PR на main; затем обновить дочернюю ветку, разрешить конфликты и проверить новый head/общий результат. Не удалять родительскую ветку раньше перевода дочернего PR. После принятия пакета возможен R07 по отдельному поручению; автоматически его не начинать.

> Используй project-delivery. Сначала проверь текущие ветки, PR, main, рабочую папку, фактическую версию сервера и критерии. Сохрани принятый интерфейс и чужие изменения. Выполни только порученное действие, сам подготовь изолированные QA-данные и доказательства. Не создавай дубликат PR и не переходи к соседним шагам автоматически.
