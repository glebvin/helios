## Decisions

- Project-scoped zones and work types are real records with tenant/project composite references. Director maintains them; master/PTO see assigned projects. Work type carries unit, required RD flag, material-control requirement and predecessor/ID requirement flags. Required RD reference is server-validated. No normative efficiency or invented norms.
- New tasks: zone, work type, title, civil workDate, positive exact decimal quantity, assigneeEmployeeId, responsible user and planned start/end interval. Validate date/range/real timezone and single-day semantics. Time intervals are necessary to permit several non-overlapping assignments in a day; reject overlapping published assignments for the same employee across projects. Do not pretend legacy tasks without intervals were checked.
- Director/master prepare/read drafts in their visible projects. Director approves/publishes (initial authority pending full matrix); master submits to approval. Worker sees own published tasks, never drafts/pending approval. PTO read only. No arbitrary supplied status.
- State sequence draft → pending_approval → published; rejection/reopen to draft with reason; cancellation with reason. Published plan immutable in this slice; later corrections/production states explicitly deferred. Publication stores immutable plan/evidence snapshot plus audit. Existing legacy status names remain for existing rows.
- One immutable/versioned yes/no front template family per project, director maintained. Master/director records complete answers for a task; server computes pass/warnings, snapshot and actor/time. Latest attempt including failed and latest template required. Editing plan invalidates old front run (separate plan revision or equivalent trusted binding). No client trusted pass/material/ID statuses.
- Publication transaction rechecks current actor/project authority, active employee assignment, exact current admission (reuse personnel evaluator in same transaction), latest front result/template/plan binding and time overlaps. Missing prerequisites fail with explicit reasons, no receipt/effect. Deterministic project → employee → tenant membership → task/assignment-related locks consistent with personnel02a (avoid reverse lock acquisition). Include actual PG race tests.
- Material/ID/hold-point modules are not implemented yet: a work type requiring these dependencies must fail publication as unsupported/not_ready. No default true for predecessors/materials. Later phase04 must replace block with real records. Do not claim full readiness TZ6.2 accepted now.
- Durable commands use requestId, expectedVersion, transactional receipt+audit and exact replay semantics already established. Reuse small existing helpers where justified; do not duplicate eligibility logic or silently widen personnel write rights. Preserve cross-operation requestId mismatch. Server checks references and all validations; RLS/grants/indexes.
- Close obvious creation bypass: legacy POST /api/tasks must not continue creating published tasks without checks. It may be retired with explicit 410 and replacement v1 path in docs; update foundation test to use an explicit controlled fixture for its existing transaction/job assertion rather than weakening the assertion. Legacy task/sync/report workflow is not certified; managed02b tasks must not execute through legacy mutations before phase03 adds validated execution (reject with clear workflow_not_supported). Existing legacy fixture task behavior may remain for compatibility testing; document this boundary.
- No task/photo uploads, real material lots, AOSR, full matrix routes, normative hours, multiple-executor attribution, physical-phone offline or production/load claim. Keep roadmap pending for these. No UI/main edits, merge/deploy, dependency churn.
