## Outcome and boundaries

A worker can start a project shift, work on own published managed task, record breaks/downtime with reasons, switch tasks, finish shift and submit exact performed volume. Server consumes retried/delayed events safely and exposes scoped real execution/time/report records. This is03a server protocol, not a complete phone offline feature: local browser queue, binary files/photos, tabular hours approval/Excel and physical-phone verification are later03b. Quality acceptance/matrix/material/ID remain04. No invented accepted volume/confirmed hours or normative efficiency; submitted result stays provisional until reviewed in later module. No UI edits.

## Core decisions

1. **Separate presence and work.** Use project-bound employee shifts, one open managed shift per employee across tenant projects. A shift has contiguous nonoverlapping segments: idle, work(taskId), break, downtime(reason code/comment, optional task attribution). Shift start opens idle. Switching mode atomically closes previous segment and opens next; finishing closes last segment. Work on two tasks never runs simultaneously for one employee. Time spent idle/break/downtime is distinct from productive task time. A shift is not copied onto each task. Existing legacy shift/report tables/tests are retained; do not make them authoritative for managed execution.
2. **Concrete event API.** Prefer one strict tagged-union POST/api/v1/execution/events with a bounded batch (max50) plus a few paged scoped read routes, rather than many equivalent mutation routes. Shapes must include stable event/requestId, employeeId, projectId, client-chosen shiftId for start so subsequent offline events can refer to it, expected employee-execution version (0 only on first stream), occurredAt explicit RFC3339 offset, optional previousEventId dependency. Kinds: shift_start, segment_change, shift_end, submit_volume. Reports may use a stable client report UUID. Do not trust actor/role/tenant from body. Normalize exact quantity with existing strict parser, no floating point rounding. Geo metadata at shift marks may be strictly typed optional coordinates/accuracy/capturedAt, clearly client reported; no proof-of-presence or photo support claim in03a.
3. **Ordering/retries.** Shared durable receipt namespace (tenant,actor,requestId) and canonical command hash must remain compatible with02a/02b. Event success, employee-stream version, domain rows and audit/receipt are one transaction. Exact retry returns original success/status after current authority recheck, despite later state/version; changed payload/kind/path conflicts. Failed event leaves no receipt/version/effects. previousEventId (when supplied) must be a successful execution event for same actor/employee/project, not an unrelated people/task receipt; missing dependency gives retryable per-item failure with no writes. Same-batch ordered events see prior committed success. Reject duplicate IDs in batch or define deterministic mismatch behavior; outer malformed body no effects. Process items sequentially with separate transactions and explicit per-item success/duplicate/error, so one failure does not roll back earlier committed independent items. Never silently reorder or discard client events. A dependent item stays blocked until its predecessor succeeds; client retains failed/pending events. Concurrent devices conflict via expectedVersion; UI will need a visible resolution state.
4. **Time.** Persist occurredAt and server receivedAt separately for every event, actor and original immutable payload/hash. Interval events must be chronological (no negative durations/overlap); new shift cannot overlap earlier closed managed shifts for same employee. Equal-time transitions may be zero length and must be explicitly handled. Client clocks are not proof: mark delayed/future/suspicious timestamps for review using documented thresholds; do not silently replace client time. Store exact integer millisecond durations/decimal strings in reads, all totals provisional/reported, not payroll-confirmed. Clip per-day intervals by tenant civil timezone with DST, no CURRENT_DATE/server timezone guesses or double counting. Open interval totals need an explicit asOf/source and cannot be presented as final. Reject malformed calendar/offset/excess precision with existing parser reused/exported as appropriate. Keep report event timestamp semantics explicit (can report a finished shift; volume must link to actual task work recorded in that shift and stay single counted).
5. **Authority.** Worker writes only own employee via current link and current tenant/project membership; director or assigned master can register for another employee only with a nonblank onBehalfReason retained in audit/event. PTO read only. Fresh server authority after waits, not cached Guard role. Shift_start requires active project assignment/admission. Starting/switching into work or submitting volume requires own published managed task on same shift project, matching assignee, active assignment, exact current admission/evidence and qualification valid on task.workDate. Reuse evaluator same PoolClient, never duplicate. Unsupported/material/ID publication already blocks upstream. Cancelled/draft/pending/foreign/legacy task cannot start work or submit managed volume. Ending/switching out of an existing interval must not require a still-valid admission (otherwise stale certificate strands time), but still requires current actor authority; an authorized director/master may close an archived/revoked assignee's existing shift with onBehalfReason. Worker who loses tenant/project access cannot submit and needs authorized manager to resolve. No invitation/role administration/full matrix here.
6. **Locking.** Maintain receipt reservation → project by key → employee by key → sorted tenant memberships/current links → applicable project membership → execution stream/shift/segments/task/assignment. Employee serializes cross-project shifts and task publication; no second-project locks after employee. Task hint/stream references are not trusted; fresh rereads after lock waits, changed hint aborts without backwards lock acquisition. Existing people archive path never waits on project, so avoid inversions with it. Existing task cancel/publish and template/assignment updates serialize on project. Streams/per-event receipts are durable. RLS/FORCE, tenant/project/employee compositeFK, unique open-shift/segment constraints and immutable accepted event ledger; no app DELETE. Do not introduce Redis/extra service/dependencies/serializable retry machinery without a concrete need.
7. **Read models.** Add a few real paged project-scoped execution shift/segment/report reads and employee/day time breakdown, own-only worker. Director global, master/PTO explicit project grants, no exposure through legacy desk endpoints. Integrate new real managed data into v1 overview additively without double counting legacy fixture rows, adding explicit provisional execution fields if needed; preserve existing fields/meaning or document narrowly necessary changes. Submitted quantity is separate from accepted (still null/unavailable for managed reports), no quality/ID fabricated. Existing task plan status remains published/cancelled, separate execution status derived from events. Legacy managed fences remain; new execution must not open old unsafe routes. Existing foundation job tests preserved. No background queue needed merely to insert a volume row; keep atomic pg-boss behavior if a required integration reuses existing job model.
8. **Verification.** Actual HTTP/PostgreSQL, all roles/tenants/projects/own scope; strict union/date/quantity/input refs; whole start→work→break→downtime→switch→end→volume chain; exact durations no copied shift; day/DST/midnight clipping; duplicate/concurrent replay and two-device conflict; dependency failure then retry; partial batch failure; no loss/effects on failure; injected post-write rollback; current role/link/assignment/archive/qualification/cancel races using real PG gates; competing cross-project starts exactly one; manager cleanup after invalidated admission; immutable event/grants/RLS/compositeFK; migration apply+repeat. Preserve all old business assertions and operation inventory, extend OpenAPI/docs with precise client protocol and limits. Full pnpmtest/APItsc and domain explicit-typeRoots fallback; plain domain TS2688 is known tooling issue, not newly fixed.
